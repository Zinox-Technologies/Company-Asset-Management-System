## 1. Purpose

A centralized web application for registering, assigning, tracking, transferring and managing company assets through their full lifecycle, including **ownership** and **ownership transfer**.

## 2. Golden rule

**Never overwrite history.** A transfer or reassignment closes the old record and creates a new one. Previous owners, assignees, dates, reasons and approvers must always remain retrievable.

## 5. Asset statuses

`Available`, `Assigned`, `Under Maintenance`, `Lost`, `Damaged`, `Disposed`, `Pending Transfer`

### Allowed status transitions

| From | To |
|---|---|
| Available | Assigned, Under Maintenance, Lost, Damaged, Disposed |
| Assigned | Pending Transfer, Available (on return), Under Maintenance, Lost, Damaged |
| Pending Transfer | Assigned (approved), Assigned (rejected, back to original) |
| Under Maintenance | Available, Assigned, Damaged, Disposed |
| Damaged | Under Maintenance, Disposed |
| Lost | Available (if found), Disposed |
| Disposed | (final, no transitions out) |

## 6. Asset ID format

`ZNX-<CAT>-<5-digit sequence>`, for example `ZNX-LAP-00125`.

## 7. Core business rules

1. Only `Available` assets can be assigned.
2. An asset has exactly one current owner and at most one current assignee at a time.
3. **Owner** is the accountable entity (employee, department or business unit). **Assignee** is the person currently using it. They may differ (e.g. owner: IT Department, assignee: John Doe).
4. Assigning creates an `Assignment` record. Returning closes it (sets `dateReturned` and `conditionOnReturn`) and never deletes it.
5. A transfer is a request, then an approval, then an effect:
   - Request creates a `Transfer` with status `Pending`; the asset moves to `Pending Transfer`.
   - On approval: the old assignment closes, a new one opens, the owner and assignee update, the transfer is marked `Approved` and the asset returns to `Assigned`.
   - On rejection: the transfer is marked `Rejected` and the asset returns to its previous status.
6. A transfer records: asset, previous owner/assignee, new owner/assignee, transfer date, reason, requested by, approved by, status.
7. A user cannot approve their own transfer request.
8. Assets that are `Disposed` cannot be assigned, transferred or edited, except to view.
9. Warranty status is computed: `Active`, `Expiring Soon` (within 90 days, configurable), `Expired`.
10. Every create, update and status change on assets, assignments, transfers, maintenance and disposal writes an **AuditLog** entry (who, what, when, before and after).
11. Passwords are hashed (bcrypt). Secrets live only in `.env`, never in Git.

## 8. Main workflow

```
Asset Registration
  -> Ownership / Assignment
  -> Employee / Department receives asset
  -> Transfer Request
  -> Approval
  -> New Owner / Assignee
  -> Transfer History updated
```

### Demo scenario (seed this data)

- Asset: `ZNX-LAP-00125`
- Owner: IT Department; Assignee: John Doe; Location: Abuja Head Office; Status: Assigned
- Transfer to Jane Doe on 30 September 2026
- Reason: Staff reassignment; Approved by: IT Manager
- Result: John Doe's assignment is closed, Jane Doe's is opened, transfer history shows both

## 9. Data model

### User
`name, email (unique), passwordHash, role, department (ref), isActive, createdAt`

### Department
`name (unique), code, head (ref User), createdAt`

### Location
`name, branch, address, createdAt`

### Category
`name, code (e.g. LAP), createdAt`

### Asset
`assetId (unique), category (ref), name, model, serialNumber (unique), purchaseDate, cost, warrantyExpiry, location (ref), condition (New | Good | Fair | Poor), status, currentOwner { type: Employee|Department|BusinessUnit, ref }, currentAssignee (ref User, optional), notes, createdBy, createdAt, updatedAt`

### Assignment
`asset (ref), assignee (ref), owner { type, ref }, assignedBy (ref), dateAssigned, dateReturned (null while active), conditionOnReturn, statusAfterReturn, notes`

### Transfer
`asset (ref), previousOwner, previousAssignee, newOwner, newAssignee, fromLocation, toLocation, reason, requestedBy, approvedBy, status (Pending | Approved | Rejected), requestDate, transferDate, decisionNote`

### Maintenance
`asset (ref), type (Repair | Service | Inspection), description, vendor, cost, dateIn, dateOut, loggedBy, createdAt`

### AuditLog
`user (ref), action (e.g. ASSET_REGISTERED, ASSET_ASSIGNED, TRANSFER_REQUESTED, TRANSFER_APPROVED, ASSET_RETURNED, MAINTENANCE_LOGGED, ASSET_DISPOSED), entityType, entityId, assetId, before, after, timestamp`

### Counter
`key (e.g. "asset-LAP"), seq`
